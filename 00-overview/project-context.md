# 看见音乐发行产品体系拆分：项目背景与现状基线

> 更新时间：2026-09-09  
> 文档定位：本仓库的核心背景文档，用于统一后续产品架构、商业模式、产品包装与 Roadmap 设计的上下文。  
> 注意：仓库为公开仓库，因此本文只沉淀可公开/低敏的产品事实与聚合结论；客户名单、原始分账数据、精确内部成本、具体客户特殊合同条款等敏感信息不写入仓库。

---

## 1. 项目为什么要做

现有“星球发行”长期承载了过多类型的用户、服务和商业关系：独立音乐人、厂牌、版权公司、聚合发行商/大型 CP 等在同一套产品和服务体系中合作；合作发行、企业发行基础设施、自助发行等不同商业模式也混在一起。

结果是：

- 产品定位不够清楚；
- 不同客户获得的实际服务等级差异很大，但产品层没有清晰表达；
- 大量低价值/低收入 CP 与高价值头部 CP 共用相近的发行能力与人工服务入口；
- 大量内容长期占用存储、发行、客服与运营资源，但部分 CP 几乎不产生收入；
- SaaS、白标、开放 API、星球发行前台等能力已经存在，但没有被整理成统一、可售卖的企业产品；
- AI 音乐带来的大规模、标准化、自助发行需求不适合继续完全沿用传统版税分成合作模式。

因此本项目不是“新增两个产品”，而是重构看见音乐的整个发行产品体系。

## 2. 三条产品线

### 2.1 星球发行

**产品本质：Managed Distribution / 合作发行。**

继续由看见音乐运营，面向音乐人、厂牌、版权公司及其他 CP。现有星球发行用户前台就是这条产品线的用户侧 Portal。

未来升级为三个合作等级：

- 基础版 Basic
- 专业版 Professional
- Plus

三个版本不应只是“菜单功能套餐”，而应同时体现：

1. 合作准入与客户价值；
2. 系统使用额度；
3. 服务等级与人工支持；
4. 商业政策与分成政策；
5. 增值服务权益。

现有用户先默认处于专业版，后续再根据收入、曲库规模、服务需求、合作深度、战略价值等指标重新评估。

### 2.2 星球发行·企业版

**产品本质：面向希望自己开展音乐发行业务的企业客户，输出发行基础设施。**

两种主要交付方式：

#### A. White-label SaaS

向企业提供一整套带有客户品牌的发行平台，通常包含：

- 企业运营/管理后台；
- 面向其音乐人、厂牌、CP 的发行前台；
- 内容、发行、DSP、合同、报表、分账等核心能力；
- 账号、组织、角色、站点品牌等租户能力。

#### B. API

客户已有自己的产品，只按需接入看见的能力模块。目标方向包括：

- Catalog / 内容与曲库 API
- Artist / Label / CP API
- Release / Distribution API
- Delivery / DSP API
- Rights / Contract API
- Reporting API
- Royalty / Split / Settlement API
- Copyright / Registration API

注意：当前系统内存在大量 API 权限，并不等于所有能力都已经达到正式对外开放 API 的成熟度。企业版后续必须做一轮 “API Ready / 可商业售卖” 盘点。

企业版商业模式方向：

> 基础接入/部署费 + 功能模块开通费 + 周期性使用费，并可按部分能力叠加 Usage-based Billing。

White-label 与 API 应采用不同价格体系。

### 2.3 AI 音乐发行（阶段性名称）

**产品本质：面向 AI 时代的付费自助发行平台。**

市场阶段可以使用“AI 音乐发行”名称，但系统设计不应该把 AI 音乐和普通音乐拆成两套底层发行模型。

产品应同时支持：

- AI 生成音乐；
- AI 辅助创作音乐；
- 普通音乐作品。

核心体验：

> 上传作品 → 填写/生成 Metadata → 选择发行渠道 → 付款 → 审核 → 上线状态 → 报表/收益管理。

与星球发行不同，不再以传统版税分成作为主要收费方式。需要重新设计付费模型，主要候选方向：

- 按单曲/专辑付费；
- 按发行渠道收费；
- 按服务期限收费；
- 按月/按年订阅，不同档位包含不同发行数量；
- 上述模式的混合方案。

同时需要明确 AI 音乐可发行渠道及不同 DSP 的 AI 内容政策。

## 3. 当前系统真实结构

目前应把现有系统理解为“一套发行/SaaS 基础设施 + 不同操作端”，而不是多个完全独立系统。

```text
                 现有 SaaS / 发行基础设施
                           │
            ┌──────────────┴──────────────┐
            │                             │
      企业管理后台                   CP / 音乐人发行前台
 Management Console                     Portal
            │                             │
 企业运营团队/内部运营使用          看见自己运营时 = 星球发行
```

未来理想结构：

```text
                 Shared Distribution Platform
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
       星球发行             企业版            AI音乐发行
  Managed Distribution   Distribution OS      Self-service
          │                   │                   │
   看见运营的 Portal      White-label/API     自助发行 Portal
```

核心原则：

> **一套发行 Domain，多种商业产品。共享能力，不复制三套发行系统。**

---

## 4. 当前星球发行前台能力与流程

现有星球发行是面向音乐人/厂牌/CP 的发行前台，属于常规数字发行 Portal。

当前核心流程：

1. 注册/登录；
2. 账号认证；
3. 签署总协议；
4. 创建/管理艺人；
5. 创建专辑、歌曲、视频等内容；
6. 上传物料并提交发行；
7. 每次发行签署对应的专辑授权书；
8. 查看审核/发行状态；
9. 每月查看看见后台计算并推送的版税和报表；
10. 前台发起提现，后台财务/运营审核后打款。

合同结构目前主要是：

- 先签署数字发行总协议、商用总协议等框架协议；
- 每次发行再签署专辑授权书；
- 在线签约使用电子签能力完成。

重要约束：

- 用户目前不能自行下架；
- 改资料、下架等事务通常需要联系客服/运营处理；
- 版权争议等问题也主要通过运营、法务、邮件或一对一沟通处理。

## 5. 当前人工服务现状

当前系统功能本身在不同 CP 之间差异不大，真正已经自然形成差异的是服务模式。

### 普通客户

- 标准客服入口；
- 下架、改单、版权问题等需要人工介入；
- 常规审核、报表、提现等按标准流程处理。

### 头部客户

- 专属运营；
- 一对一对接；
- 专属沟通群；
- 更高优先级的问题处理；
- 商务条件可能单独协商；
- 重点客户可能获得额外推广支持。

因此 Basic / Professional / Plus 的设计重点不应是“是否拥有核心发行能力”，而应逐步转向：

> **核心发行能力 + Quota + 服务等级 + SLA + 商业条件 + Add-on 权益。**

---

## 6. 成本与分层的核心矛盾

当前大量低价值 CP 长期占用内容存储、发行资源和人工支持成本。

拟重点研究的限制/计量维度包括：

- ISRC 数量；
- UPC 数量；
- 艺人数量；
- 专辑/发行数量；
- 曲库规模；
- 存储规模；
- 年度新增发行量；
- 改单/下架等人工服务次数；
- 客服/运营服务等级。

设计目标不是简单“把原有免费能力收费化”，而是改善：

1. 大量内容占用存储但不产生商业价值的问题；
2. 长尾客户消耗人工服务成本的问题；
3. 高价值客户与普通客户服务等级无法清晰表达的问题。

后续需要重点研究 Ditto Music、DistroKid、TuneCore、CD Baby、Amuse、LANDR 等海外发行产品的商业模式，尤其关注：

- 订阅 vs 按发行付费；
- 艺人数量限制；
- 发行数量限制；
- ISRC/UPC 政策；
- 作品长期存储/下架政策；
- Add-on；
- 客服等级；
- AI 音乐政策；
- 长尾用户运营成本控制方式。

## 8. 历史 SaaS 商业模式参考

历史 SaaS 曾经采用过以下商业模式组合：

- 元数据管理；
- 内容存储；
- 版税分账；
- 发行能力；
- 综合套餐；
- 发行/传输 Usage Billing；
- 本地化部署；
- API 交付。

历史报价采用过“基础费 + 模块 + 曲库/用户/传输量等用量”的思路。

这些历史价格与套餐结构只作为背景，不应直接沿用。其真正价值是证明：

> 看见过去已经尝试过 Module + Quota + Usage 的商业化方式，企业版可以在此基础上重新标准化，而不是从零定义。

## 9. 客户结构的聚合结论

当前客户结构同时包括：

- 大量独立音乐人；
- 小型/中型厂牌；
- 大型厂牌；
- 版权公司；
- 聚合发行商/大型 CP；
- AI 音乐或其他批量内容客户。

收入高度集中在极少数头部客户：头部约数十家 CP 贡献绝大部分收入，而大量长尾用户的收入贡献很低。

因此版本划分不应简单按“个人/企业”或“音乐人/厂牌”分类，而应综合考虑：

- 年度发行收入；
- 有效曲库规模；
- 年度新增发行量；
- 独家程度/合作深度；
- 服务消耗；
- 战略价值。

初步产品逻辑：

```text
Basic
- 大量长尾客户
- 标准化、自助化
- 控制额度和人工成本

Professional
- 有稳定业务价值的发行客户
- 更高额度、更好服务、较优商业条件

Plus
- 极少数头部/战略客户
- 专属运营、定制服务、最高优先级和最优商务条件
```

具体准入阈值尚未确定。

## 10. 宣发推广的边界

资源位申请、内容推广、投流等不属于星球发行的核心发行服务，应保持为独立的音乐营销/推广产品线。

星球发行的不同等级可以获得跨产品权益，例如：

- 优惠；
- 免费额度；
- 战略客户权益；
- 优先服务。

但不能重新把推广业务混入星球发行的核心产品定义。

## 11. 统一产品架构原则

### 11.1 一套发行 Domain，多种 Product Packaging

未来应尽量共享：

- Identity / Organization
- Catalog
- Artist / Label / CP
- Asset
- Rights
- Contract
- Release
- Delivery
- DSP / Channel
- Compliance
- Reporting
- Royalty
- Settlement
- Billing
- Entitlement / Quota

星球发行、企业版和自助发行都是这些能力的不同组合，而不是三套独立业务模型。

### 11.2 UI 与 AI 都应该是操作端

长期架构应支持：

```text
            User
              │
      ┌───────┴───────┐
      │               │
      UI             Agent
      │               │
      └───────┬───────┘
              ▼
         Capability
              │
            Domain
              │
             Data
```

让系统能力既可被 UI 使用，也可被 AI/Agent 安全调用。

### 11.3 商业产品与底层系统解耦

- Basic / Professional / Plus 是商业合作等级，不应该复制发行系统；
- White-label 是统一租户化产品，不应每个客户复制一套业务代码；
- AI 音乐不是一个独立的底层内容类型；
- API 应逐步由内部接口升级为稳定、可售卖的 Capability Contract。

## 12. 当前最重要的待设计事项

### 星球发行

- Basic / Professional / Plus 准入标准；
- Quota 与 Entitlement 体系；
- 存储/曲库/艺人/发行数量限制；
- ISRC / UPC 使用规则；
- 不同等级 SLA 和人工服务；
- 改单/下架/版权问题等服务政策；
- 分成与商业政策；
- 老用户迁移方案；
- 与音乐推广产品之间的跨产品权益。

### 企业版

- 当前能力盘点；
- White-label 标准能力边界；
- 品牌定制范围；
- API Ready 能力清单；
- API 模块化产品结构；
- 新报价体系；
- Setup / Module / Subscription / Usage 的组合；
- 首批可直接对外展示的能力。

### AI 音乐发行

- 按发行付费 vs 订阅制；
- 不同套餐的发行数量；
- 单曲/专辑定价；
- 渠道与服务期限定价；
- AI 音乐可发行 DSP 清单；
- DSP AI 内容政策；
- 收益模式；
- 自助审核和风控成本；
- 与星球发行之间的用户迁移/升级关系。

## 13. 建议的后续工作顺序

1. **海外发行产品商业模式研究**  
   重点研究成本控制、艺人/发行数量、订阅、Add-on、AI 音乐等。

2. **星球发行 Basic / Professional / Plus v0.1**  
   先建立版本设计框架，不急于一次确定所有数值。

3. **企业版 Current Capability Inventory**  
   将现有管理后台、星发前台、开放 API 对齐，区分：系统已有 / 客户可用 / 可白标 / API Ready / 可售卖。

4. **企业版产品包装与首期对外能力**  
   优先满足近期已有客户沟通需求。

5. **AI 音乐发行商业模式研究与 Pricing v0.1**。

6. **统一 Entitlement / Quota / Billing 模型**。

7. **整体产品 Roadmap 与用户迁移 Roadmap**。

---

## 14. 当前核心判断

截至 2026-09-09，本项目已经形成以下核心共识：

> **看见未来不是维护三个发行系统，而是在统一发行基础设施上经营三种不同的发行产品和商业模式。**

> **星球发行的升级核心不是功能增删，而是把客户价值、服务成本、使用额度和合作深度真正产品化。**

> **企业版不是“一个后台”，而是 White-label Distribution OS + API。**

> **AI 音乐发行不是新的底层发行类型，而是新的 Self-service Distribution 商业产品。**
