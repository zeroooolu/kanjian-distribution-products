# 星球发行·企业版：真实业务基线 v0.1

> 日期：2026-09-10  
> 状态：Confirmed Business Baseline  
> 用途：作为企业版产品定义、Demo、定价、API 与后续 Roadmap 的事实基线。

---

# 1. 核心结论

企业版不是重新设计一套虚构的发行系统，而是把看见音乐已经存在的发行供应链、多租户能力、开放接口和结算体系产品化，提供给企业客户运营其下游 CP / 厂牌 / 音乐人。

真实主链路为：

```text
租户下游 CP
   ↓
租户发行平台
   ↓ 自动传输
看见音乐
   ↓ 审核
DSP
```

因此企业版的核心价值可以概括为：

> 企业通过自有品牌平台或 API 接收下游内容，看见音乐负责底层发行供应链、审核与 DSP 交付。

---

# 2. 参与角色与责任边界

## 2.1 看见音乐

- 企业版基础设施提供方；
- 与企业租户签署合作合同；
- 接收租户发送的发行内容；
- 承担看见侧发行审核；
- 通过现有发行链路发送至 DSP；
- 接收 DSP 报表及结算；
- 进行收益分账；
- 在满足可提现条件后执行打款。

## 2.2 企业租户

- 企业版直接客户和合同主体；
- 经营下游 CP / 厂牌 / 音乐人；
- 可使用品牌发行平台或 API 接入；
- 支持多个管理账号和前台账号；
- 下游内容提交后，可按系统规则自动发送给看见。

## 2.3 下游 CP / 厂牌 / 音乐人

- 由企业租户经营和管理；
- 向租户提交发行内容；
- 不需要与看见音乐单独签署合作合同；
- 不作为企业版 P0 中看见侧的直接 KYC / Contract Counterparty。

## 2.4 DSP

- 内容最终交付平台；
- 看见作为主要发行链路中的直接交付方；
- 向看见提供业务报表，并按各自结算周期完成结算。

# 3. 真实发行 SOP

当前确认的默认 SOP：

```text
1. CP 在租户体系提交发行
        ↓
2. 内容进入租户
        ↓
3. 租户系统自动传输给看见
        ↓
4. 看见执行发行审核
        ↓
5. 审核通过后发送 DSP
        ↓
6. 跟踪交付 / 上线 / 异常状态
        ↓
7. 后续支持更新、重传、下架等发行操作
```

### 产品设计约束

- P0 不应强制增加“租户人工审核”环节；
- 租户审核可以作为未来可配置能力，但不是默认真实链路；
- 看见审核是当前主链路中的关键控制点；
- 企业版 Demo 必须明确表现“租户侧提交”和“看见侧审核”是两个不同系统角色。

# 4. DSP 能力基线

本轮提供了现有 DSP Metadata 表。

表中包含的核心配置维度包括：

- DSP 分组 / 分组属性；
- DSP 名称 / ID；
- 渠道标签；
- 可发行地区；
- 启用 / 禁用状态；
- 前台 / 后台可见；
- 内容挑选方式；
- 可接收物料；
- 结算权利项；
- 结算类型；
- 结算周期；
- 报表周期；
- 对接类型；
- 物料传输方式；
- 上下架对接方式；
- 传输情况；
- 交付周期；
- SP 信息。

当前表中共有约 526 条非空 DSP 配置记录，其中：

- 启用：207 条；
- 前台可见：100 条；
- 后台可见：138 条。

> 注意：配置记录数不等于可对外宣传的“正式发行渠道数”。官网和销售资料应另行建立 Public Channel Catalog，只使用确认可对外展示的有效渠道口径。

启用记录中已经同时存在数字发行、商业发行、数据授权等不同渠道类型，并覆盖专辑、歌曲、MV 等不同物料形态。

### 对企业版的意义

企业版的“发行网络”不应该只是一排 DSP Logo，而应逐步升级为可查询的渠道能力矩阵：

```text
DSP
├── 可发行地区
├── 支持内容类型
├── 是否需要挑选
├── 交付周期
├── 报表周期
├── 结算周期
└── 当前可用状态
```

这会成为企业客户评估发行基础设施的重要产品能力。

现有星球发行后台已经具有较完整的内容与发行 API 能力。

当前确认的接口能力分类至少包括：

## 内容相关

- 艺人；
- 专辑；
- 歌曲；
- 整体内容；
- 厂牌；
- DSP 管理；
- 文件；
- AI 生成；
- ISRC / UPC。

## 公共服务

- 国家和地区 Code；
- 语种；
- 角色；
- 风格等基础字典能力。

## 发行相关

当前可见能力包括：

- 创建模版；
- 获取模版列表；
- 获取模板详情；
- 编辑模版；
- 创建发行预览；
- 发行设置概况；
- 发行列表查询；
- 以及现有发行相关接口组中的其他接口。

### 企业版 API 产品化原则

企业版不应另起一套业务 API，而应在现有能力上增加标准企业开放层：

```text
现有发行 Domain / API
          ↓
Enterprise API Gateway
          ↓
鉴权 / 租户隔离 / 配额 / 日志 / Webhook / 文档 / Sandbox
          ↓
企业客户系统
```

后续需要拿到完整 API 文档后，再做 Endpoint Mapping 和缺口表。

# 6. 技术交付能力

当前确认支持：

- DDEX；
- XML；
- Excel；
- SFTP；
- API。

因此“企业级深度接入”不是未来概念，而是已经有真实技术底座的能力组合。

产品化时建议将其理解为“接入与交付方式”，而不是强行做成第三套独立产品：

```text
企业发行平台
发行 API
        ↓
共享底层能力
        ↓
API / DDEX / XML / Excel / SFTP
```

# 7. 账号与多租户能力

当前管理后台与星球发行前台均支持多个账号。

因此企业版 P0 不需要从零证明“是否能有多个用户”，而应重点补齐企业级产品层：

- 企业租户；
- 租户管理员；
- 租户普通成员；
- 下游 CP / 厂牌账号；
- 权限与数据隔离；
- 品牌与域名配置；
- API Credential 与租户绑定。

P0 暂不需要无限层级的 Sub-distributor Tree。

# 8. 合同与 KYC 边界

当前确认：

> 只需要企业租户与看见音乐签约。

因此主合同关系为：

```text
看见音乐 ← 合同 / KYC → 企业租户
                         ↓
                   下游 CP / 厂牌
```

下游 CP 不需要与看见重复签约。

这进一步确认：

> 企业租户是真正的 Operator，而不是普通星球发行中的一个大 CP。

# 9. 收益、报表与提现基线

真实流程：

```text
DSP 生成报表
    ↓
看见接收 DSP 报表
    ↓
看见按 CP / 租户进行分账
    ↓
形成报表收益
    ↓
等待 DSP 对应款项实际结算到账
    ↓
转为可提现金额
    ↓
租户 / CP 发起提现
    ↓
看见执行打款
```

### 最重要的产品规则

**报表收益 ≠ 可提现金额。**

至少应区分：

```text
报表收益 Reported Revenue
待结算 Pending Settlement
可提现 Available Balance
提现处理中 Withdrawal Processing
已打款 Paid
```

只有 DSP 对应报表款项已经实际结算到账后，对应收益才进入可提现范围。

这一规则必须进入企业版 Demo、API 状态模型和财务产品定义，不能简单只展示一个 Balance。

# 10. 历史商业报价与成本基线

当前确认曾存在两类企业合作报价：

## 模式 A：按量

- 历史报价约：¥0.5 / 每次 / 每渠道；
- 业务计量本质可理解为“单首内容向单一渠道发生一次发行传输”。

## 模式 B：年度合作

- 历史报价：¥25,000 / 年。

此前内部报价资料中的一个专业版样例为：

- ¥25,000 / 年；
- 含 100,000 次发行传输；
- 超额传输曾按 ¥1 / 次 / 首报价。

### 已知底层成本口径

历史内部成本资料中的主要技术成本：

- 存储成本：约 ¥0.05 / 首 / 年；
- 发行传输成本：约 ¥0.02 / 次 / 首；
- 一次传输定义为“一首歌发送至一个平台”。

当前仍缺审核人工、客户服务、异常处理、财务结算等完整服务成本，因此不能只按技术传输成本直接推导最终售价。

# 11. 对此前产品假设的修正

## 11.1 Default Review Flow

此前假设：

```text
CP → 企业审核 → 看见最终 QC → DSP
```

修正为真实默认链路：

```text
CP → 租户 → 自动传看见 → 看见审核 → DSP
```

企业审核可作为未来可配置能力，不作为 P0 默认流程。

## 11.2 DSP Deal Model

行业竞品常见 Own Deal / Provider Deal / Hybrid。

但看见当前企业版主链路明确为：

```text
租户 → 看见 → DSP
```

因此：

- P0 官网和 Demo 以“看见发行网络”作为主模型；
- Own Deal / Hybrid 不作为 P0 核心卖点；
- 后续只有在真实客户明确提出、且看见业务允许时再产品化。

## 11.3 White-label 术语

国内企业对外不使用 White-label 作为主要名称。

当前推荐：

> **品牌发行平台**

对内仍可用 White-label 描述行业模式。
