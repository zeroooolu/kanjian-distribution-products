# 星球发行·企业版：商业模式 v0.1

> 日期：2026-09-10  
> 状态：Commercial Working Baseline  
> 上游：`business-baseline-v0.1.md`

---

# 1. 商业模式目标

企业版的商业模型不沿用普通星球发行“CP 分成”作为主逻辑。

企业版本质上出售的是：

> **发行基础设施 + 发行网络 + 企业级服务能力。**

因此主要收入应来自：

```text
平台服务费
+ 使用量费用
+ 企业级接入 / 定制服务
+ 可选高级能力
```

而不是单纯依赖版权收益分成。

---

# 2. 已知历史报价

目前已有两种真实历史模式。

## 2.1 按量模式

历史报价：

> **约 ¥0.5 / 首 / 渠道 / 次**

一次发行传输可定义为：

> 一首内容向一个 DSP 发生一次有效传输。

例：

```text
1 首歌
× 10 个 DSP
= 10 次传输

按 ¥0.5 / 次：
= ¥5
```

该模式适合：

- API 接入；
- 业务规模仍不稳定；
- 希望按实际发行量付费的客户；
- 试运行和早期客户。

---

## 2.2 年度模式

历史报价：

> **约 ¥25,000 / 年**

此前内部报价样例曾包含：

- ¥25,000 / 年；
- 100,000 次发行传输；
- 超额曾按 ¥1 / 次 / 首计价。

该模式更适合：

- 品牌发行平台；
- 有稳定发行量的企业；
- 需要预算可预测的客户；
- 需要持续运营服务的客户。

---

# 3. 已知成本基线

历史内部资料中的技术成本口径：

```text
存储成本：约 ¥0.05 / 首 / 年
发行传输成本：约 ¥0.02 / 次 / 首
```

其中一次传输指：

> 一首歌传输至一个平台。

### 直接技术毛利示意

若按 ¥0.5 / 次销售：

```text
销售单价     ¥0.50
技术传输成本 ¥0.02
----------------
传输层毛利   ¥0.48
```

该数值只反映已知传输技术成本，不能视为完整毛利。

尚未完整计入：

- 看见发行审核；
- 发行异常处理；
- 客户服务；
- 商务与交付；
- 财务分账；
- 提现与打款；
- 技术支持；
- 企业实施；
- 特殊 DSP 运营成本。

因此正式定价不应简单按 ¥0.02 成本乘固定倍率生成。

---

# 4. 推荐商业结构

企业版建议长期保留两条购买路径，而不是强制所有客户进入统一套餐。

## A. 按量合作

适合 API / 平台型客户。

建议结构：

```text
基础接入
+
发行传输用量
+
可选企业服务
```

核心 Meter：

> **有效发行传输次数**

即：

```text
歌曲数 × 渠道数 × 实际传输动作
```

P0 可以延续历史约 ¥0.5 / 首 / 渠道 / 次作为报价参考线，但是否正式保留该价格需要结合客户规模重新验证。

---

## B. 年度企业合作

适合品牌发行平台和稳定规模客户。

建议结构：

```text
年度平台服务费
+
包含一定发行传输额度
+
超额用量
+
可选高级模块 / SLA
```

历史 ¥25,000 / 年可继续作为一个重要市场验证锚点，但正式产品不建议只写“无限发行”。

原因：

- 每次 DSP 交付仍有真实成本；
- 大客户与小客户规模差异极大；
- 审核和异常处理成本随发行量增长；
- API 客户可能存在高频自动化调用。

因此年度套餐应该保留 Quota / Fair Use / Overage 机制。

---

# 5. 不建议的定价方式

## 5.1 不以 API Request 数量作为主计费单位

API 请求次数与实际商业价值不一致。

一次发行可能调用几十个接口，但真正产生供应链成本的是：

- 内容规模；
- 发行量；
- DSP 交付；
- 收益处理；
- 企业服务。

API Request 只适合作为技术 Rate Limit，不适合作为核心商业 Meter。

## 5.2 不直接采用“无限发行”

除非合同中已经包含明确的业务规模假设，否则无限发行会导致：

- 极端客户占用大量人工审核；
- DSP 异常处理成本放大；
- 年费收入与业务量完全脱钩。

## 5.3 不把版权分成作为唯一收费方式

企业版客户购买的是基础设施能力。

若只通过版权分成收费，会让高收入客户成本过高、低收入但高发行量客户反而无法覆盖服务成本。

---

# 6. 推荐计费维度

企业版后续 Plan / Quote Engine 建议支持以下维度：

## 基础维度

- 年度平台服务；
- 发行传输次数；
- 曲库规模；
- 下游 CP / 厂牌数量。

## 高级维度

- 品牌发行平台；
- API；
- DDEX；
- XML；
- SFTP；
- 批量导入；
- 数据 / 报表接口；
- 收益处理；
- 专属技术支持；
- SLA；
- 定制开发 / 实施。

### 推荐原则

客户报价不需要把所有维度全部逐项收费。

这些维度首先用于：

> 判断客户属于哪个规模档位，以及是否产生额外服务成本。

---

# 7. 建议的产品化形态

P0 官网定价页可以先采用两种合作方式：

| 合作方式 | 适合客户 | 计价逻辑 |
|---|---|---|
| 按量合作 | API / 试运行 / 波动型业务 | 按实际发行传输量 |
| 年度合作 | 品牌发行平台 / 稳定规模企业 | 年度服务费 + 包含额度 + 超额 |

企业级 DDEX / SFTP / 特殊实施等能力不单独做第三个套餐，而作为：

> **企业定制项**

进入商务报价。

---

# 8. 与行业定价模式的关系

当前同行产品的公开定价普遍不是单一 API Request Billing。

行业中常见的企业计价维度包括：

- Tracks / Catalog Size；
- Label / Client Accounts；
- Monthly Royalties Processed；
- Support SLA；
- Platform / White-label；
- API Capacity。

星球发行企业版可以吸收这种“按业务规模分层”的方法，但不需要照搬美元 SaaS 套餐。

看见已有按传输量计费的历史经验，因此更适合建立：

```text
平台费
+
发行传输 Meter
+
规模与服务分层
```

形成更符合自身成本结构的商业模型。

---

# 9. P0 定价页建议

在正式价格审批前，官网可以先展示：

## 按量合作

> 按实际发行传输量计费，适合 API 接入和弹性业务规模。

## 年度合作

> 年度平台服务 + 发行额度，适合长期运营发行服务的企业。

## 企业定制

> DDEX、SFTP、特殊渠道、迁移、实施与 SLA 根据项目范围报价。

不建议在官网立即公开历史 ¥0.5 和 ¥25,000，除非内部确认这两个数字仍可作为当前标准对外价格。

---

# 10. 下一步验证

商业模式下一轮只需要验证三个问题：

1. ¥0.5 / 首 / 渠道 / 次是否仍可以作为 2026 标准按量价格；
2. ¥25,000 / 年是否仍作为标准年度价格，包含多少传输额度；
3. 企业品牌平台 / API 是否需要单独一次性实施或接入费用。

这三个问题确认后即可形成 `commercial-model-v1.0.md`，并直接落到正式 Pricing 页面。
